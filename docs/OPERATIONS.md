# Running and maintaining PeopleOS

This guide is for the person running the application. For code changes, use [DEVELOPER_GUIDE.md](DEVELOPER_GUIDE.md). For API contracts and authorization, use [API_REFERENCE.md](API_REFERENCE.md) and [SECURITY.md](SECURITY.md).

## 1. Start the application and backend

Use Node.js 20.9 or newer and run commands from the project folder:

```sh
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000). One custom Node process serves the website, `/api/*` backend routes, and `/api/live` WebSocket endpoint. There is no separate Express server or second backend port to start. `server.mjs` is the entry point.

Development works with the public demo accounts before external services are configured. MongoDB-backed accounts, persisted organization data, and live database notifications require the integration settings below. The demo uses fictional browser-local records and cross-tab events.

The development server defaults to the local loopback interface. To choose another port:

```sh
npm run dev -- --port 3001
```

Stop with Ctrl+C. Restart the process after changing `server.mjs`, environment variables, or server configuration. Normal React/API code changes reload during development. A development refresh caused by editing the source is separate from normal in-app navigation; profile/list navigation preserves the workspace shell.

## 2. Demo login

The login screen displays three accounts and lets you prefill the fields:

- Administrator: `alex@peopleos.co`
- HR Manager: `lana@peopleos.co`
- Employee: `olivia@peopleos.co`

The shared public demo password is `PeopleOS@2026!`.

These credentials select sample views. They do not create MongoDB users, authenticate private workspace APIs, or authorize access to a real company. Browser storage retains demo edits and images. Clear only PeopleOS demo storage if you want to reset that browser's sample records.

Demo access is enabled by default in development, disabled by default in production, and can be explicitly controlled with `ALLOW_DEMO_ACCESS=true` or `false`. Keep production demos disabled unless a public sample showcase is intended.

## 3. Connect external services later

Copy the environment example when you are ready:

```sh
cp .env.example .env.local
```

Set actual values locally. `.env.local` is ignored by Git; do not place credentials in browser code or documentation.

1. **Authentication secret:** replace `NEXTAUTH_SECRET` with a long random value, for example generated by `openssl rand -hex 32`. Keep it stable across restarts and shared across all application instances.
2. **Application URL:** set `NEXTAUTH_URL` to the exact public URL. Development normally uses `http://localhost:3000`; production uses the HTTPS domain. This also establishes the trusted public origin behind a reverse proxy.
3. **MongoDB:** set `MONGODB_URI` and `MONGODB_DB`. Use a database user limited to this application database, TLS, and network access limited to the application host. The app creates indexes used for tenant isolation and uniqueness.
4. **Google, if used:** set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. Register the authorized redirect URI as `<NEXTAUTH_URL>/api/auth/callback/google`. Google sign-in requires a verified email and an active membership, or first-workspace onboarding for an identity with no existing membership.
5. **Initial organization:** choose stable `WORKSPACE_ID` and `WORKSPACE_NAME`. `ADMIN_EMAILS` applies only to Google bootstrap in that configured workspace. Each organization has its own server-issued or explicitly configured ID.
6. **Hosting:** provide a long-running Node host, HTTPS, and reverse-proxy WebSocket upgrade support. Static hosting and serverless-only request handlers cannot run `server.mjs` as a persistent WebSocket server.

Changing these values requires restarting the Node process. `/api/config` reports whether configuration values are present; `database: true` does **not** confirm that the database connection succeeds.

## 4. Create the first real password account

After configuring MongoDB and the authentication secret, use the trusted operator CLI. It loads `.env.local`, prompts for a masked password and confirmation, and never prints the password:

```sh
npm run user:create -- \
  --workspace-id acme \
  --workspace-name "Acme Studio" \
  --email admin@example.com \
  --name "Workspace Administrator" \
  --role admin
```

Choose your own organization ID, email, name, and a new password. The first member of an empty organization must be an administrator. The CLI preserves suspended memberships and refuses to silently change existing roles. `--help` shows its options without contacting a database.

For non-interactive operation, the script supports `PEOPLEOS_INITIAL_PASSWORD`. Supply that through a secret manager or protected process environment; do not put a real password in a committed script, shell argument, or shared command transcript. Remove the temporary value after use.

Sign in with the real account's email and password. An administrator can then add members in **Workspace & access**, open a member's detail page, and choose **Set sign-in password**. Passwords require 12–128 characters. The account's workspace role comes from its active database membership.

Google sign-in is an alternative. Verified users without memberships can create their first workspace. Existing suspended or revoked memberships cannot use onboarding to obtain another tenant.

## 5. Optional sample data in MongoDB

The browser demo needs no seed command. If you deliberately want fictional data in a configured test tenant:

```sh
node --env-file=.env.local scripts/seed.mjs
```

The command writes to `WORKSPACE_ID` in the configured database. Use a test organization, verify the target first, and do not run it against a real organization merely to test connectivity. It uses namespaced IDs and preserves existing scoped rows and roles. It does not create public demo passwords in MongoDB.

## 6. Production process

After supplying production secrets and external integrations:

```sh
npm ci
npm test
npm run build
npm start
```

The build script uses Next.js webpack. Keep `npm start` under the hosting platform's process supervisor. Configure `PORT` and `HOST` for that host; bind publicly only behind the intended HTTPS ingress. Restrict database access separately.

The reverse proxy must forward WebSocket `Upgrade`/`Connection` headers for `/api/live` and permit persistent connections. Browser connections use `wss:` on HTTPS. All instances must share the same MongoDB database and `NEXTAUTH_SECRET`. Credential rate limits are process-local; a production ingress should add shared abuse protection.

Do not enable production demo accounts to solve a real-account configuration problem. Do not publish real values from `.env.local` when asking for help.

## 7. Verification after a change

```sh
npm test
npm run build
```

Then check the affected UI in the browser:

- Log in with each relevant role; verify allowed and denied direct URLs.
- Open an employee from a list, use its related-record links and breadcrumbs, then use browser Back/Forward. The sidebar and existing session should stay mounted.
- Check loading skeletons, an empty result, a validation error, and a successful save.
- If changing styles, check light/dark mode, Arabic RTL, selected fonts, and a phone-width screen.
- If changing charts, check tooltips with pointer and keyboard and confirm the chart card does not move.
- If changing exports, download both formats and verify the authorized current results.
- If changing authentication or notifications, check logout, revoked access, password reset, reconnect behavior, and workspace separation.

The unit suite uses in-memory database fixtures. Live Google and MongoDB verification must be performed after those integrations are configured.

## 8. Troubleshooting

**Port already in use:** stop the previous PeopleOS process or choose another port. Do not run two servers against the same Next development output directory.

**Google button unavailable:** OAuth values are missing. Email/password demo accounts can still work in development.

**Real email/password fails:** verify the member is Active, a password was provisioned in the correct tenant, MongoDB is reachable, and the configured secret is stable. Errors deliberately avoid revealing whether an email exists. Repeated failures are rate limited.

**Invalid request origin:** ensure the browser URL and `NEXTAUTH_URL` match the intended public service. The shared origin helper handles the custom server's internal listening address; it deliberately ignores untrusted forwarded host/protocol headers.

**Workspace unavailable:** inspect service configuration and sanitized server errors. Do not paste a MongoDB URI containing a password into logs or chat.

**Notification reconnecting:** confirm `server.mjs` is running, the secret and database are configured, membership remains Active, and the proxy supports WebSockets. The server checks MongoDB about every two seconds; a replica set is not required.

**A route returns HTTP 200 but redirects:** Next can stream redirect metadata after sending headers. The browser still navigates to sign-in or the authorized dashboard. Test API authorization separately; private APIs return 401/403 rather than relying on UI redirects.

**A photo or QR scan fails:** use JPG/PNG/WebP, respect the 2 MB photo limit, and scan a complete PeopleOS code for a profile already available to the current account. Camera access needs browser permission and a secure context; image upload and manual employee-ID lookup are alternatives.

## 9. Backups and recovery

Back up MongoDB with the database provider's tools and test restores in a separate environment. Preserve the stable application secret in a secret manager. Never replace production credentials with the public demo password.

Exports are reports, not complete database backups. Real data deletion is currently permanent through the application; recovery depends on database backups. Demo data can be reset independently in browser storage. Activity/notification writes are best effort and do not constitute an immutable audit archive.
